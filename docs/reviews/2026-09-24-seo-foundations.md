## Defects and what was done

### 1. BreadcrumbList shown as "Unnamed item" in Search Console — a cosmetic label, now named

Search Console's URL inspection labels each detected structured-data entity by its `name`. The
site's `BreadcrumbList` nodes had well-formed `ListItem`s (each with `position`, `name`, and a
string `item` URL, exactly Google's documented shape) but the list itself had no `name`, so the
report showed the entry as "Unnamed item". That label is cosmetic: the breadcrumbs were valid and
eligible, and the label is not an error, a warning, an eligibility defect, or a ranking factor.
Naming the list only makes the report readable.

`breadcrumbJsonLd` is the single generator used by every page with breadcrumbs (about, contact,
sell, privacy, FAQ, tours, all `/properties/*` sections and kinds, every listing, both locales),
so one change covers all of them. The name is the visible trail in the page's language, no new
copy. `›` is Bidi-mirrored, so Arabic trails read correctly right-to-left.

While writing the semantic tests, a related gap surfaced: section pages (`/properties/*`,
`/tours/`) supply their own `CollectionPage` node with the same `@id` as Head's automatic WebPage
node, which wins the dedupe, and it carried no `breadcrumb` reference. `collectionPageJsonLd` now
accepts `breadcrumbId` and both callers pass it, so every page with a BreadcrumbList has a
WebPage-family node pointing at it.

## Fourth revision (same day): Codex final-clean-pass finding, fixed

Codex's final clean-pass review of the third revision returned **CHANGES REQUIRED** on one point:
the third-revision skip rule keyed on `dist/` alone, so if a listing that is still in the source
data ever failed to build, its test would skip as "delisted" and the deploy gate would stay green
over a missing page. Fixed as follows, in `test/seo-jsonld.test.mjs` only:

- Source truth, verified in `src/pages/properties/[slug].astro` and `src/pages/ar/properties/[slug].astro`:
  `getStaticPaths` emits a page for every entry of `listings` whose slug is not in `reservedSlugs`,
  with no status filter. So a listing in `src/data/listings.json` must have both routes in `dist/`.
- The test now reads `src/data/listings.json` with `readFileSync` + `JSON.parse` (no TS import)
  and applies that rule. `listingSkipReason(slug)` returns a skip reason only when the slug is
  absent from the source or is one of the reserved section slugs (`houses`, `apartments`, `land`,
  `buildings`, `for-sale`, `for-rent`, `off-plan`, `international`, mirroring `reservedSlugs` in
  `src/lib/listings.ts`); otherwise it returns null and the test runs. `requireBuiltListing(route)`
  then fails with an explicit "in the source but missing from dist/" message if the page was not
  built. All previous assertions inside the four tests are unchanged.
- A new red-capable self-check (`self-check: the listing skip rule tells "absent from source" apart
  from "in source but not built"`) proves the helpers behave as described: an unknown slug yields a
  skip reason, a source-present slug yields none, a reserved slug yields the reserved reason, and a
  source-present route that is absent from a built-page map throws. Test count: 19.
